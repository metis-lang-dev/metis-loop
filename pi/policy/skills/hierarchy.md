Procedures distilled from two hand-written hierarchies (ALFWorld's, ScienceWorld's; metis-worlds */docs/HIERARCHY.md, scienceworld/experiments/REPORT.md §2). Follow them unless a record contradicts them.

1. A rule's NAME says what the world does. `verb` or `verb_why` sends that verb's command with the variables the table names; any other rule only moves the program's own tokens and sends nothing. Never start a bookkeeping rule with a verb.
2. A result is the WORLD's word, never the rule's. An action and its answer are two rules: the first sends the command and leaves a token (`taking(O)`, `moving(R)`); the second consumes that token together with the world's own line for it (the `said(KIND)` event: moved, picked, opened, connected, waited, looked …) and the next beat's facts, and only then produces the result. A rule that reads the world's answer in the same beat it acted reads the world as it was BEFORE the action.
3. Lift, and keep the left side to what the action NEEDS. A rule names no thing: variables typed by the declarations, static facts read with `$`, the instance's facts separate from the base. A static fact goes on the left side only when the world refuses the action without it; a static that merely happens to be true in the record (`$notopenable(R)`, `$otype(O, _)`) decorates the rule and makes it fail on the next record of the same action. One rule per action, general over every record of that action — never a second rule for the same action with the other value of a static. When records of the same action are shown, write the rule that explains all of them.
4. The policy is tokens of the program's own. World rules say what an action does; tokens say when to act (`want(O)`, `start`, `ready`). Guard an action rule with a token so the program pursues the task instead of wandering; produce the next token on the right side.
5. One consumer per goal per state. For any state, at most one rule fires for a given goal token: give every refusal its own rule with a `%%` line that says why (`not_here`, `no_door`, `wrong_dest`), so a refusal is a result the planner can read, never a stall.
6. Split by what is asked, not by what is seen. A specialist takes a GOAL in (`goto(R)`, `get(O)`, `test(O)`, `put(O, C)`) and puts a RESULT out (`reached(R)`, `got(O)`, `conducts(O)`/`insulates(O)`, `placed(O)`) or a refusal (`elsewhere(R)`); it sees only the world facts it needs. The planner knows WHAT and asks HOW: it holds the task's facts and turns each result into the next goal; it never acts in the world.
7. An experiment is a chain with a verdict. When a property is hidden, the rules build the test (wire, heat, wait), then LOOK, then read the answer from the world's facts after the look (`state(bulb, on)`), carrying the parts they chose in tokens.
8. Prefer the smallest declaration that fits. A new predicate needs a declaration in the base's namespace; a token's arity should carry only what the later rules need.
